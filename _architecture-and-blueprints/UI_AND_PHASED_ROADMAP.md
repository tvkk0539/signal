# UI Architecture & Phased Roadmap

This document outlines the strategic, phased approach to developing the User Interface (UI) across both the web and mobile platforms. Attempting to build the entire swarm control interface at once is an anti-pattern; instead, we follow strict, iterative milestones.

---

## 1. The Phased Web UI Roadmap

To avoid "UI Blindness" and scope creep, the React web frontend will be built in distinct phases.

### Phase 1: The Foundation (MVP Browser)
*   **Goal:** Prove the foundational `rclone` WebSocket pipeline works.
*   **UI Components:**
    1.  **Authentication Screen:** A simple, secure Login/Register form (JWT based).
    2.  **File Explorer:** A single-pane grid/list view similar to standard Google Drive.
*   **Functionality:** Connects to a *single* worker. Allows the user to view directories, upload a file, and download a file. All advanced swarm and media features are disabled or hidden.

### Phase 2: The Command Center (Swarm Control)
*   **Goal:** Introduce distributed swarm management.
*   **UI Components:**
    1.  **Fleet Sidebar:** A new side panel listing all connected, authenticated ephemeral workers (e.g., "Worker 1 [GitHub] - IDLE", "Worker 2 [AWS] - BUSY").
    2.  **Global Task Queue:** A bottom overlay window displaying aggregate progress bars for multiple simultaneous tasks across different workers.
*   **Functionality:** The user can highlight multiple folders and assign different backend workers to process them simultaneously.

### Phase 3: The Media Engine (WebRTC)
*   **Goal:** Implement zero-delay media streaming.
*   **UI Components:**
    1.  **Media Player Modal:** A custom video/audio player overlay.
*   **Functionality:** Clicking a media file initiates the WebRTC signaling process with the Relay Server and opens a direct UDP pipe to the assigned worker for live streaming.

## 2. Mobile App Architecture (Android & iOS)

Developing for both Android and iOS simultaneously is achieved efficiently without requiring massive hardware investments (like dedicated macOS build servers) for initial development and testing.

### A. The "Write Once, Run Anywhere" Strategy
The `/mobile` directory will be built using **React Native**.
*   The UI code is written once using React components (e.g., `<View>`, `<Text>`).
*   The React Native bundler natively compiles these components into Java/Kotlin (for Android) and Objective-C/Swift (for iOS).
*   This guarantees 100% parity in features and business logic across both platforms.

### B. Cross-Platform Testing (The Expo Framework)
To test the iOS application without owning an Apple computer, we utilize the **Expo** framework.
1.  The developer runs the Expo development server locally (`npm start`).
2.  The developer installs the free "Expo Go" client app on their physical Android and iOS devices.
3.  By scanning the QR code generated by the development server, the Expo Go app instantly loads the custom mobile interface over the local Wi-Fi network.
4.  **Hot-Reloading:** Any saved code changes instantly reflect on both the Android and iOS screens simultaneously.

### C. Platform-Specific Configurations
While the business logic is shared, the mobile app requires specific OS-level configurations:
*   **Permissions:** React Native modules handle requesting native OS permissions (e.g., accessing the camera roll, writing to external storage for massive binary downloads).
*   **Background Tasks:** Utilizing the Native OS Download Managers (as detailed in the Mobile Architecture blueprint) ensures that large file transfers continue smoothly even when the user minimizes the app or turns off their screen.
